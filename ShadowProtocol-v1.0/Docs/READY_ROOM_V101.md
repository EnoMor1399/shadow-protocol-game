# Native Unreal ready room

## Source implementation

`ASPObserverPlayerController` now exposes `RequestReadyState(bool)` and
`RequestSpawnGroup(FName)` for local UI. They call reliable server RPCs on the
owning controller. The RPCs accept no player id, session id or player-state
pointer: the server obtains its own controller's player state.

GameMode accepts changes only from an authoritative player in this world's
roster, connected and assigned a competitive team, during Planning/Waiting.
Authentication is required by the authenticated-session setting and always by
the dedicated admission gate. Dedicated edits also require a registered,
non-draining backend and an available OSS session. Spawn choices must match a
configured group available to the player's team; changing the choice clears
readiness. Preparation and live rounds reject these mutations.

Requests have a shared local 200ms throttle and a server 100ms throttle per
controller. These limit mutation frequency, not incoming network bandwidth.
Invalid or throttled requests leave replicated state unchanged. The UI displays
server state rather than optimistically granting readiness.

The native `USPReadyRoomWidget` is created for local controllers only and added
to their player screen. During Planning it shows admission status, team, current
spawn and ready count with a Ready/Cancel button. It uses UI-only input while
visible and returns to game input when planning ends. Teardown removes the
widget. `bShowNativeReadyRoom=false` lets a Blueprint controller use custom UMG;
wire its buttons to the same Request methods. The native panel does not include
a spawn picker: a custom UMG picker can call `RequestSpawnGroup` with configured
ids. No binary widget or map assets were generated by this patch.

The native panel targets authenticated matches. For offline test maps with
session authentication disabled, use a custom test UI or disable the panel.

`BeginPreparation` rechecks current ready state before proceeding, including
when an asynchronous OSS start finishes after a player withdraws readiness.

## Verification boundary

Nine Node source-contract checks guard the C++ wiring; they do not compile or
execute Unreal C++, RPC transport, Slate layout or widget focus. UE 5.6 is not
available in the editing container. Run the builds in
`ONLINE_GAME_SESSION_V101.md`, then verify with packaged client/server:

1. Before admission, Ready is disabled and no request can change server readiness.
2. After admission, each client changes only its own ready state; other clients
   see the replicated count. A request never accepts another player's identity.
3. Unknown and opposing-team spawn groups are rejected. Valid changed groups
   reset readiness and update the replicated selection.
4. The tenth ready player permits countdown. Cancel before preparation resets
   the planning countdown; repeat with delayed OSS start completion.
5. Replay ready and spawn requests during preparation/action and after match
   completion; server values must remain unchanged.
6. Burst requests and disconnect during planning. Verify no premature start,
   stale UI, stuck cursor or unexpected input lock after map travel.
7. Check mouse, keyboard/controller focus, split-screen ownership and ten-player
   replication on a real UE build. UI-only input is presentation behavior, not
   server-side prevention of pre-round movement/combat.

Backend session expiry/reconnect UI, trusted platform bootstrap, Steam/EOS and
packaged multiplayer/soak validation remain pending.

Reference: [Epic RPC ownership documentation](https://dev.epicgames.com/documentation/en-us/unreal-engine/remote-procedure-calls-in-unreal-engine).
